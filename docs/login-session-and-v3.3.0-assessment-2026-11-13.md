评估日期：2026-11-13。对象：本地 main（`5f3ed8a`）、服务器导出的 `logs/xianyu_2026-11-03.log`、官方 tag `v3.3.0`（`16bd475`）。只做日志、源码、隔离复现和合并预演，没有修改业务代码、执行实际合并或操作服务器。

## 结论

本次确定发生了闲鱼登录 Session 失效，且自动续期没有成功。聊天 WebSocket 仍响应心跳，不能证明卖家订单接口和发货接口可用。未配置密码登录凭据，Session 失效后系统无法通过该路径自动重新登录；相关通知还被错误过滤。

浏览器刷新链路持续受阻是最值得优先修复的工程问题。代码存在取消排队任务后泄漏浏览器槽位的缺陷，已在隔离进程复现。日志与槽位受阻相符，但不能仅凭这份日志确定最初占槽的任务、当时剩余槽位及服务器资源状态。

不建议直接用官方镜像或源码覆盖魔改版。可以在保留当前代码的基础上合并 v3.3.0，但该版本没有修复上述续期、告警和浏览器槽位问题，升级本身不能解决本次故障。

## 源码问题与复现

### 1. 浏览器等待取消后可能泄漏槽位

`utils/browser_limit.py:138` 使用 `asyncio.to_thread(semaphore.acquire, True, 300)` 获取线程信号量。取消等待的协程不会终止正在运行的线程；稍后其他浏览器释放槽位，该线程仍会取走槽位，但协程已经取消，拿不到 `LimitedBrowser`，也就没有对象负责归还。

`XianyuAutoAsync.py:7887` 对整个 Cookie 刷新设置 180 秒超时，短于槽位等待的 300 秒。排队超过 180 秒便可能触发上述缺陷，逐步耗尽可用槽位。超时分支 `7935–7937` 未记录具体超时原因，finally 的“Cookie刷新完成”容易造成误判。

隔离复现调用真实 `browser_limit.launch_browser`，让信号量暂时无空位、取消等待协程、再释放空位：等待线程取走空位，最后非阻塞取槽失败。复现结果：`Cancelled waiter consumed a later freed slot: True`。没有启动浏览器、访问闲鱼或使用真实账号。

修复应确保取得槽位后的所有取消路径都有明确归还方，区分排队时间和实际浏览器操作时间，记录等待/运行/超时/成功状态。不能仅延长超时或提高并发上限。服务重启可以重置进程内信号量，是临时缓解手段；真正失效的 Session 仍需重新登录。

### 2. 登录失效通知被误过滤

`XianyuAutoAsync.py:5544` 的 `_is_normal_token_expiry` 将 `Session过期`、`FAIL_SYS_SESSION_EXPIRED` 和定时 Token 刷新失败都列为免通知关键词。`5410` 的通知函数在发送前直接跳过。日志 26207 行明确显示该误过滤。

通过 AST 提取当前版本和 v3.3.0 的真实纯函数执行：“检测到Session过期，但未配置用户名或密码，无法自动刷新Cookie”在两个版本中均返回 `True`，因此都会被屏蔽。应按错误码和恢复结果分类：可恢复签名令牌更新允许静默，真实登录失效且恢复失败必须发一次明确告警，并提供账号页重登状态。

### 3. 登录态失效后的业务请求没有统一停止

`XianyuAutoAsync.py:2455` 失败后设置 `needs_relogin`，但 Token 刷新循环仍每 10 分钟重试，WebSocket 心跳及部分业务任务继续运行。`utils/xianyu_seller_api.py:291` 对所有卖家接口异常都按页重试，Session 失效后仍翻页，日志累计 140 条“某页已重试 3 次”的 Session 过期记录。它们不是 140 次独立掉线。

应在确定认证失效时结束当前翻页，统一标记账号待重登，并暂停依赖认证的主动业务请求；重登验证通过后恢复。界面应区分聊天连接状态与订单/发货认证状态。

### 4. 跨循环锁与错误上报

`utils/risk_control.py` 的进程级账号 guard 含 `asyncio.Lock`；HTTP 路由及账号监听/同步运行于不同事件循环，可共用同一个 guard。日志实际出现跨循环锁异常，调用路径与该风险一致，但日志没有完整堆栈，不能最终确认具体锁的拥有者。

应统一账号业务操作的事件循环或采用明确支持跨线程/循环的限流实现，并让同步异常进入失败结果；当前 `utils/seller_order_sync.py:268` 只记录异常，接口可能仍显示 0 单、0 失败及成功响应。
