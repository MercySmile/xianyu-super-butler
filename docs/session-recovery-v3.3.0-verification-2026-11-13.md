# 登录保活、发货恢复与 v3.3.0 合并验证

日期：2026-11-13。分支：`codex/session-recovery-v3.3.0`。

原魔改提交：`5f3ed8a`；第一阶段登录恢复修复：`f9d1f40`；合并目标：官方固定 tag `v3.3.0`（`16bd475`）。后续并发保护与测试修正包含在本地合并提交中。

**仅完成本地代码、构建与测试，没有推送远程、部署服务器、登录真实闲鱼账号或执行真实订单发货。**

## 修复后的行为

- 浏览器等待使用可取消的非阻塞取槽，不再留下后台线程窃取后续槽位。启动取消/失败及重复关闭均验证只归还一次。
- 浏览器 Cookie 刷新期间继续维持聊天心跳，不再为刷新主动暂停监听。排队/刷新超时记录为失败，成功时间只在卖家接口认证通过后更新；失败按退避间隔重试。
- Token 续期不受买家消息冷却影响，并结合平台返回的有效绝对到期时间提前刷新。扫码首次缺少签名令牌时，会合并响应 Cookie 后有界重试，不误判为必须重登。
- 读取真实数据库字段 `value`，重新加载人工更新的 Cookie。Token 刷新串行执行；较早的浏览器和订单同步快照不会回滚较新的签名令牌。
- Cookie 落库串行并使用条件更新：只有数据库仍保留本轮所刷新 Cookie 时才替换，后台旧结果不能覆盖新扫码结果，也不能重新创建已删除账号。更新仅涉及 Cookie 值，保留账号密码、所有者及发货配置。
- Session 失效和普通令牌轮换分开处理。Session 失效及续期失败不会被“正常过期”通知过滤；没有自动重登凭据时，明确进入待扫码状态，并发送一次重登通知。实际通知送达仍取决于账号已配置可用通知渠道。
- 已配置账号密码时，尝试自动重登，校验返回的账号身份，随后验证 Token；保留监听实例并重新建立消息连接。连续失败有上限，避免重试风暴。平台要求扫码或人工验证时仍需要人工处理。
- 卖家接口认证失效时立即终止翻页，同一客户端不重复请求已失效会话。恢复操作投递到实际监听循环，多个失效请求共用一次恢复；旧监听或旧扫码会话的失败不能干扰新监听。
- 网络超时/断线持续退避重连，不会仅因为连续断线而强制密码登录、扫码或重启实例。心跳长期无响应或连续发送失败时关闭失活连接，让主循环重新连接。
- 登录恢复成功重新连接后，执行原有漏单补偿。认证未恢复、连接不可用，或异步查询/规则检查期间变成不可用时，不获取新库存。
- 限流 guard 不再跨事件循环共享 `asyncio.Lock`，改为线程锁保护短时间令牌计算，等待发生在锁外。同步异常、Session 失效及失败页不再显示为“0 失败、同步成功”。
- 监听任务意外退出时，管理器使用数据库最新 Cookie 自动拉起；主动取消、停用、删除或已替换的监听不会因此被恢复。

## 魔改保留

与修复前 `5f3ed8a` 对比，下列实现保持一致：

- `app/card_inventory.py`：分组卡密的库存切分和组合规则。
- `app/delivery_attempt.py`：持久化处理权、消费边界和重复出库拦截。
- `app/delivery_template.py`：组合内容和分段发送。
- `frontend/components/CardList.tsx`、`frontend/components/ItemList.tsx`：分组库存与固定文本组合发货配置界面。

`app/delivery_reconciliation.py` 保留原有真实订单校验、规格选择和防重入口，并增加认证恢复中的保护。核心发货路径在库存/API 消费前再次检查认证和连接状态。

合并时业务源码中的重登冲突保留完整修复；`static/` 中冲突的产物由合并后的前端源码重新构建。版本标识为 `3.3.0`。

关键用例覆盖：

1. 等待浏览器过程中取消，后续空位仍可正常获取；浏览器启动取消和关闭失败不泄漏/重复归还槽位。
2. 同一账号在两个线程的不同事件循环中同时等待限流，不再出现循环绑定错误。
3. 模拟连续 72 小时、73 次 Token 更新，同时持续接收消息，签名与数据库凭据保持更新。
4. 实际主循环收到 Session 失效后保持待扫码状态，不反复建连；更新 Cookie 后重新连接并启动心跳、Token 任务及漏单补偿入口。
5. 密码重登、失败阈值、账号身份校验、自动续期通知分类、Cookie 刷新超时状态。
6. 手动扫码与后台刷新竞争、并发持久化、已删除账号迟到的刷新结果。
7. 网络连接连续失败不强制重登；半开连接通过心跳超时重新连接。
8. 分组卡密加固定文字的组合订单：待重登时不扣库存，恢复后完整发送一组内容，再次补偿不重复消费。
9. 订单详情或发货规则检查期间发现认证失效，不扣库存、不发消息。
10. 原有多规格、多数量、并发手动/消息/补偿、库存不足、部分发送失败、确认平台发货失败及重启后防重回归。

## 验证边界与后续服务器验收

72 小时用例为**模拟时间与接口响应**，并非服务器实际连续运行 72 小时。真实闲鱼可能撤销登录、要求短信/扫码/人工验证；代码无法保证永久免登录。当前没有配置密码的账号，一旦平台已撤销 Session，系统会明确提示扫码，不会伪装为可发货。

后续获得部署指令后，应先备份数据库和现有程序，部署包含魔改与本次修复的自建版本，不切换官方 `latest` 覆盖本地功能。使用测试订单验证在线发货、短时断线重连、扫码恢复后的漏单补偿及通知实际送达，再观察 48–72 小时。全量订单兜底同步继续受原有系统开关和间隔控制，重新连接会额外触发补偿。

已有出库但发送不确定的订单仍采用保守策略，保留人工核对拦截；不能自动重新扣卡强行补发。生产验收前，本地测试通过不代表真实短信/扫码风控、服务器浏览器环境或真实订单已验收。
