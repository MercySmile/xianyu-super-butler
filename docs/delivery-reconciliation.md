# 自动发货漏单补偿

自动发货现在有三种入口，共用原有商品、规格、库存和拦截规则校验：

- 聊天中的付款通知。
- “等待卖家发货”状态提醒：合并短时间内的重复提醒，约 2 秒后查询卖家真实订单，再在 5 秒后复查一次，兼容状态更新延迟。提醒中的会话号不会当作订单号使用。
- 订单同步或详情刷新发现待发货订单，以及账号连接成功后的检查。定时同步沿用系统现有的启用状态和间隔。

补偿必须重新通过卖家接口确认订单处于待发货状态，取得真实订单号、商品、买家和规格，不能仅凭本地状态或提醒文字扣库存。同一商品、同一买家连续购买不同规格，按各自订单号独立处理。规格缺失或未绑定、会话无法确定、账号停用、连接断开或风控暂停时，不会直接扣库存。

## 防止重复出库

消息触发、补偿检查和手动发货通过 SQLite 的 `order_delivery_attempts` 表竞争同一订单的处理权，跨线程、跨连接也只能由一方执行；账号重启后仍保留记录。启动时自动创建表和索引，无需手动执行 SQL。

- 已标记 `system_shipped`、已发货或已完成的订单，不再发送卡券。
- 有历史 `card_shipments` 出库记录的订单，不自动再次扣库存。
- 库存不足、规则未匹配等尚未消耗内容的失败，可以在后续检查时重试。
- 批量库存扣减与“已取出内容”的标记同事务提交。外部卡密 API 请求前也会记录这一边界。
- 已取出内容后发送失败、部分发送，或进程在处理过程中中断，会保留拦截记录，等待人工核对，避免重启后再次扣库存。清空已发货卡密列表不会清除新机制的拦截记录。
- 卡券全部发送后即记录发送完成；即使闲鱼确认发货失败，也不会再次取卡。此时使用“仅修改闲鱼发货状态”完成确认即可。

对需要人工核对的订单，先检查订单日志和卡密库存中的已发货明细，确认买家实际收到的内容；需要补消息时使用原出库卡密，然后仅确认平台发货状态。不要通过清空数据库记录强制重新扣库存。外部消息和卡密 API 无法与本地数据库组成同一个事务，因此进程突然退出的订单采用保守处理，不承诺自动恢复所有中断发送。

## 部署和验收

本次只改后端，无需重新构建前端。将修改提交并推送后，服务器拉取对应提交，再重启后端；容器部署应重建并重新创建服务。首次启动会自动补齐数据表。

使用新测试订单分别验证：普通付款消息、只有状态提醒、通过同步发现的待发货订单。同一商品连续购买不同规格时，应分别命中各自库存；已经手动发货的订单再次刷新或同步，库存数量应保持不变。

日志关键字为 `发货补偿`，会说明触发来源以及跳过原因。自动化测试使用隔离数据库与模拟平台接口，不代表服务器已更新或真实闲鱼订单已验收。
